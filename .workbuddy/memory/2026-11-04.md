## 2026-11-04 DSH 重启问题定位
- 现象：本机 DSH-web 重启失败；新机正常。
- 结论1：services.js:97 的 verify=[DeepSeek Harness.exe,--expose-internals] 匹配不到本机由 ~/.dsh/dsh-web-restart.bat 用系统 node 起的实例（cmdline: node.exe ... @deepseek-ai/dsh/lib/bin.js web），procs.js:436-450 判「无法确认是本服务」，ipc.js:339 中止重启。
- 结论2：procs.js:421 用 cwd 当命令行特征兜底，Windows 命令行不含 cwd，该兜底对 DSH 恒为空。
- 环境噪音：~/.dsh/profiles/web/cordis.patch.yml 6 处 MCP command 指向不存在的 Marvis node.exe，启动刷错误但不影响启动耗时（实测 6s 就绪）。
- 实测：管理器原命令在 3083 端口启动 6.05s 就绪 → 启动侧无问题，仅停止侧。

## 2026-11-04 卡死 + 实时状态 + 刷新按钮
- 卡死根因：IPC 路径里全是 spawnSync（netstat 8s + 最多 4 次 PowerShell 15s + taskkill 8s），阻塞 Electron 主进程事件循环，Windows 判定窗口「未响应」。
- 改法：procs.js 新增 runAsync / killPidTreeAsync / scanAsync（1 次 netstat + 1 次 CIM 同时拿端口 PID 与命令行命中）/ decideTargets（同步异步共用判定）/ stopAsync / stopAllAsync；stop()/stopAllSync() 保留同步版给 before-quit（同步钩子不能 await）。
- 周期性卡顿：detect.js 的 DETECT_TTL 15s → 5min，改成只在 refresh/安装/改设置时 invalidateDetect()。
- 日志刷屏：ipc.js LOG_FLUSH_MS=100ms 批量推送；渲染层日志上限 1200 行。
- 实时状态：procs.js 加 startedAt Map + getPid/getUptime；svc:list 返回 pid/uptimeMs；渲染层 2s 轮询 + signature 差分，只有签名变化才重建 DOM，其余就地改文本。
- 自杀保护踩坑：decideTargets 里用 process.execPath 判「是不是自己」太宽——纯 node / 开发态 Electron 下 execPath 是共享的 node.exe，会把所有 node 托管服务判成自身，导致非托管实例永远停不掉（报「端口有进程但不属于本服务」，foreign 为空）。现在只在 Electron 打包态（versions.electron && !defaultApp）才用 execPath，另外加 pid/ppid 判据。
- svc:start 先查 pm.isRunning 再探端口，避免连点两次启动叠加实例（port 从 spawn 到 listen 有空窗）。
- 测试：tools/test-restart.js 22 项、tools/test-restart-e2e.js 28 项全绿（用例 E 用 CLI 路径特征复现本机外部实例场景）。
- 环境经验：Bash 与 PowerShell 两个通道都会在命令结束时回收子进程，长驻服务没法从这里启动；WMI Win32_Process.Create 被安全策略拦截；Start-Process 在当前会话会因环境块里同时有 HTTPS_PROXY / https_proxy 抛 ArgumentException。


## 2026-11-04 开发版不显示版本号 / 检测不到更新
- 现象：从 GitHub 拉的开发版界面版本号错、更新检测失效；Release 包正常。
- 根因（同一个）：`app.getVersion()` 只在「应用根目录有 package.json」时返回本项目版本。以入口文件方式启动
  （`electron src/main/index.js`，IDE 运行配置/调试脚本常见）时 Electron 把内置默认应用当根目录，
  getVersion() 退化成 Electron 自身版本。实测：`electron .` → v1.0.4 正常；`electron src/main/index.js` → v33.4.11。
  双向后果：界面显示 v33.4.11；更新检查 current=33.4.11，latest(1.0.x) < current → newer=false → 永远「已是最新版本」。
- 修法：ipc.js 加 `managerVersion()`，按 app.getAppPath() → __dirname 上溯两级 → resources/app 依次读 package.json
  并校验 name==='qq-dsh-manager'，读不到才回退 app.getVersion()；app:version 与 update:check 都改用它。
- 第二个问题：更新检查的裸 https 不继承系统代理，且 GitHub API 未认证限额 60 次/小时/IP，
  共享出口 IP 很容易 403（本机实测 x-ratelimit-remaining: 0）。改法：
  1) API 请求优先走 Electron net.fetch（Chromium 栈，继承系统代理），失败回退裸 https；
  2) 全部 API 源失败时回退到网页版 releases/latest 的 302，从 Location 取 tag（不消耗限额），
     此时没有资产直链，前端改成「打开 Release 页面手动下载」；
  3) 解析不出三位版本号就当本次失败继续试下一个源，避免 version='' 被 cmpVer 当 0 → 永远「已是最新」。
- 注意：Electron 的 net.fetch 不支持 redirect:'manual'（抛 "Redirect was cancelled"），只能跟随跳转后读 res.url。
- 注意：本仓库 tag 形如 QQ-DSH-Manager-v1.0.10，/releases/tag/ 后面不是直接跟数字，正则要先取 tag 段再抽 \d+.\d+.\d+。
- 版本：package.json / package-lock 根字段 1.0.4 → 1.1.0（lock 里其余 5 处 1.0.4 属于 clone/defaults/globalthis/infer-owner/mkdirp，不能动）。
- 现状：GitHub 最新 Release 是 1.0.10；本地已是 1.1.0，发布时必须打 >=1.1.0 的 tag，否则用户收不到更新。
- 测试：新 e2e 用例 H（桩里 getVersion 返回 33.4.11、getAppPath 指向空目录，断言 app:version 仍等于项目 package.json 版本）。22/0 + 31/0。

## 2026-11-04 需求修正：开发版刻意关闭版本号与更新
- 上一轮把「开发版不显示版本号/不检测更新」当成 bug 修了，实际是用户想要的产品行为。已改为按打包状态区分。
- 判定口径：`app.isPackaged === true` 才算 Release 构建；`npm start` / 启动.bat / `electron <入口>` 都是开发版。
- 主进程（ipc.js）：
  - `isReleaseBuild()` 统一判定；
  - `app:version` 返回 `{ packaged, version }`，开发版 version 为 ''；
  - `update:check` 开发版直接返回 `{configured:false, packaged:false, ok:false, error:'开发版不支持检查更新'}`，不发网络请求；
  - `update:install` 开发版直接拒绝，避免写坏 update-home/update-new。
- 渲染层（app.js initFoot）：拿到 packaged=false 时把 更新按钮 / 进度容器 / 版本行 全部 remove()，页脚只留「运行中服务：x / y」。
- 验证：
  - 开发态实跑（CDP 读取）：footText = "运行中服务：2 / 3"，无 #btn-update、无版本行；app:version = {packaged:false,version:''}。
  - 打包态用桩模拟（ipc 返回 packaged:true）：页脚 "运行中服务：0 / 0 / 检查更新 / v1.1.0"，点击弹「已是最新版本 v1.1.0」。
- 测试：e2e 用例 H 重写为双向断言（开发版不暴露 / 打包版正确），22/0 + 36/0。
